GitHub can be the place where a team records intent, reviews changes and runs delivery controls. It is not automatically the runtime, the evaluator or the observability backend for every AI system. This distinction makes the following choices easier.

The examples below describe a fictional service and are starting points, not default policies. Feature availability depends on your plan, environment and organization settings.

PART 01 A shared vocabulary for agentic work

An agent is more than a model response: it works toward a goal, chooses actions, observes results and may try again. A harness supplies the execution loop, tools, context and limits around that model. A skill supplies reusable task guidance; an evaluation tests an outcome or behavior against stated criteria.

The GitHub perspective

A repository holds code and versioned instructions. A Copilot session can investigate and propose work; a pull request records a proposed change; Actions checks and human review supply different kinds of evidence. A session, a workflow run and a pull request are related records, not interchangeable names for the same thing.

Separate context from authority. A repository instruction can tell an agent how to work, but access controls and merge requirements determine what it is allowed to do. A useful answer or a passing test is evidence, not proof that every requirement was met.

Try it with your team

  1. Pick one proposed change in a noncritical repository. Write down the goal, the agent's available tools and the intended stopping point.
  2. Identify the session, commit, pull request and checks that provide evidence of what happened.
  3. Name the person who decides whether the change is acceptable and the control that enforces that decision.

Boundary: Definitions and product surfaces change. Use terms to clarify responsibility, not as a maturity score.

PART 02 AIOps complements DevOps

DevOps concerns how people build, deliver and operate software together. AIOps commonly describes using analytics or AI to help interpret operational events. They address different problems: faster pull requests do not by themselves improve incident detection, and event correlation does not establish ownership of a service.

The GitHub perspective

Issues, pull requests, commits, Actions runs and deployments can explain what changed and when. Your monitoring and observability system supplies production health, alerts and traces. Connect these records deliberately; GitHub does not become an event-correlation or telemetry backend merely because a repository contains your code.

Use a consistent service name, environment, release identifier and commit SHA where your systems support them. Compare delivery outcomes such as change lead time and deployment frequency with stability outcomes such as change failure and recovery time. Look at a service over time rather than ranking individuals.

Try it: follow one incident

  1. Start with a synthetic incident for a fictional catalog service. Link its alert to the affected service, environment and release in the incident record.
  2. Find the corresponding commit, pull request and deployment record. If a link is missing, record the gap rather than guessing causality.
  3. Open an issue for an approved fix, review the pull request and compare the next deployment with the same operational signals.

Boundary: An AI-generated diagnosis is a hypothesis. Confirm it against production evidence and keep remediation approvals appropriate to the risk.

PART 03 From an agent to a software factory

A workflow defines a process and its triggers; individual steps may or may not use AI. An agent chooses actions within its permitted tools. An automation starts work on a trigger. A software factory is a broader arrangement of people, agents, workflows and controls. Teams use these terms differently, so ask what actually runs and who makes the final decision.

The GitHub perspective

GitHub Actions workflows are versioned in the repository. Copilot automations can run agent tasks on schedules or repository events, but their configuration is stored separately from repository contents. They require an eligible private or internal repository, plan and policies. Neither a trigger nor an agent makes a factory safe to operate without review.

GitHub auto-merge waits for the configured requirements; it does not decide whether those requirements are adequate. A dark factory usually means changes proceed without someone reviewing every change. It is an operating choice, not a feature to switch on or an unavoidable goal. Some paths may always need a person.

Design a bounded first path

  1. Choose a low-risk task, such as proposing tests for a small module. Define the trigger, allowed tools, spending limit and expected pull request.
  2. Require relevant checks and human review. Use CODEOWNERS with required code-owner approval for sensitive paths; verify ruleset bypass permissions as well.
  3. Measure accepted and rejected proposals, missed problems and reversions. Only consider increasing autonomy after a risk owner reviews the evidence and rollback plan.

Boundary: Agent Merge can address selected pull request blockers; it is not the same as auto-merge and does not replace review or repository merge requirements.

PART 04 MCP and APIs solve different integration problems

An API exposes operations to software clients. Model Context Protocol (MCP) standardizes how an application connects an AI assistant to capabilities such as tools and context. An MCP server may call an existing API underneath; using MCP does not eliminate the API's authentication, rate limits or failure modes.

The GitHub perspective

Use the GitHub REST or GraphQL API directly when application code already knows the operation and sequence. Consider an MCP server when an assistant needs to discover and choose among tools during a task. The host still executes the calls and controls access; the model's choice does not grant authorization.

Copilot surfaces differ. GitHub documents that its cloud agent and code review consume MCP tools, not server-provided resources or prompts. Repository-configured tools can be used autonomously in delegated work, so evaluate permissions before enabling them rather than assuming a confirmation will appear for every call.

Try it: connect a read-only investigation

  1. Define the question and minimum data needed, such as recent issues and a specific pull request. Start with read-only operations and a narrowly scoped identity.
  2. Review the server, tool descriptions, destination and underlying permissions. Treat issue text, tool results and repository content as untrusted input.
  3. Exercise failures, timeouts and access denial. Add a separate, explicitly authorized write path only if the workflow actually needs one.

Boundary: A tool's read-only label is not a substitute for server-side authorization. Do not put credentials in the repository or in example prompts.

PART 05 Observe agents; use agents to investigate

There are two distinct questions. Observing an agent asks what happened during its run: its tools, failures, retries and result. Agent-assisted observability asks an agent to inspect operational signals and propose an investigation or fix. The first is evidence about the agent; the second is a task performed by it.

The GitHub perspective

For coding work, start with the Copilot session, pull request timeline, commits and Actions logs available for that surface. These records help a reviewer inspect the proposed work, but are not a promise that every model decision or production span is exported as OpenTelemetry.

For an agent in your own application, instrument the application and its tool calls with an observability stack. Correlate a run with the relevant release and, where appropriate, the pull request. GitHub records and application traces answer complementary questions.

Try it: create an evidence trail

  1. During an incident, give an investigation agent read-only access to the relevant signals. Ask for supporting evidence and uncertainty, not a production action.
  2. Have a person review the diagnosis before creating a scoped issue or accepting a proposed pull request. Record the session and workflow links where your policies permit.
  3. After deployment, compare the affected service's signals and capture the outcome for the next evaluation.

Boundary: Session access, sharing and retention vary by environment. Treat logs and tool results as potentially sensitive; collect the minimum needed and apply your organization's access and retention rules.

PART 06 AI observability spans the whole system

AI observability covers more than a language model. Infrastructure can be healthy while retrieval serves stale material or a predictive model's inputs drift. Conversely, an application may return plausible answers while latency, spend or downstream errors are rising.

The GitHub perspective

Use GitHub to version the application, infrastructure definitions, tests and operational runbooks, and to review the changes between releases. Your runtime platform and observability backend still need to emit and analyze the signals. Connect the two through identifiers you actually record, such as service, environment, deployment and commit.

  • Infrastructure and serving: request failures, latency, resource saturation and provider errors.
  • Data and retrieval: freshness, input distributions and retrieval relevance for the use case.
  • Application and agent: user-visible outcomes, evaluation results, tool failures and repeated steps.

Try it: map a release to signals

  1. Choose one user journey and its service owner. For each layer, identify one useful signal and the system that owns it.
  2. Record a release or commit identifier in deployment metadata and propagate trace context where supported. Verify the join rather than assuming it exists.
  3. Set an investigation and rollback path for a quality regression even when HTTP errors remain low.

Boundary: OpenTelemetry GenAI conventions are evolving. Pin the version your instrumentation emits and verify field names before relying on dashboards.

PART 07 The harness makes work executable

The harness is the surrounding software that gives a model a way to act: tool execution, context, state, limits and a stopping condition. Different harnesses using the same model can behave differently because their tools, instructions and access differ.

The GitHub perspective

Repository instructions can describe how to build, test and navigate the code. Skills can package a repeatable task. Actions provides an independent place to run checks, while rulesets and protected environments can constrain merging and deployment. Together these are parts of a delivery harness; they are not all the same as Copilot's own runtime.

Instructions are guidance, not a security boundary. Protect the underlying identity, network access, tool permissions and branch independently. Review any scripts or skills before use, and keep setup reproducible without storing credentials in the repository.

Try it: improve one repository

  1. Document the verified build and focused test commands, directory conventions and a short definition of done in repository instructions.
  2. Give the agent only the tools and environment it needs. Define what to do when a test fails, a permission is denied or a budget is exhausted.
  3. Run the same representative task several times before and after the change. Compare outcomes, unnecessary retries and reviewer corrections.

Boundary: A better harness reduces avoidable failures; it does not guarantee a correct or safe change. Human review and independently enforced checks still matter.

PART 08 Evaluate behavior, not just syntax

An evaluation asks whether an output or action meets a defined standard. A valid response can still be unsupported, irrelevant or unsafe. Use deterministic tests where an exact rule is possible, and use human review or a carefully calibrated model judge for qualities that need judgment.

The GitHub perspective

Version approved prompts, evaluation code, rubrics and non-sensitive fixtures with the application. An Actions workflow can run your chosen evaluation harness and publish appropriately sanitized results as an artifact; a required status check can gate a pull request. These are your team's evaluation components, not an automatic guarantee provided by GitHub.

Keep genuinely held-out cases outside the agent's read scope. Do not expose protected datasets or credentials to untrusted pull request code. A model judge can be inconsistent or biased by length and ordering, so compare it with human labels and investigate disagreements.

Try it: evaluate an incident summary

  1. Prepare synthetic cases: supported conclusions, missing evidence and misleading instructions. Define correctness, citation support and refusal to perform an unauthorized action separately.
  2. For a small pilot, record results per case and repeat runs. An illustrative gate might require at least 9 of 10 supported-summary cases to pass and zero unauthorized actions in 20 adversarial attempts. Agree your own criteria; these small samples do not prove safety.
  3. Compare the candidate with the previous version, review disagreements and run independent holdouts through a trusted, isolated evaluation path before changing the release decision.

Boundary: Offline tests catch known regressions; permissioned, sampled production evaluation can reveal new ones. GitHub Models was retired in July 2026, so do not design a new evaluation workflow around it.

PART 09 Observe the LLM application, not only its uptime

Traditional latency and error rates remain useful, but they do not tell you whether an answer is grounded or whether a multi-step request consumed unexpectedly many tokens. Track operational behavior, quality and cost together, with enough context to compare versions.

The GitHub perspective

Copilot usage reports help authorized administrators understand adoption and supported activity; their coverage and aggregation depend on the documented surface and policy. They are not a substitute for telemetry from an LLM application your team builds. Use application instrumentation and an appropriate backend for that runtime.

For your own system, compare provider errors, duration or time to first response, token usage, tool-call failures and sampled evaluation outcomes by release and model where available. Define what each measure includes, especially retries, cached tokens and incomplete calls, before calculating cost or trends.

Try it: define a minimum useful record

  1. Capture a trace or request identifier, service, release, duration, status and usage metadata. Add prompt or model version identifiers only when available and approved.
  2. Connect an evaluation result or user feedback to the relevant request without assuming a thumbs-down explains the cause.
  3. Default to metadata. Collect prompt, response or retrieved content only with an approved purpose, redaction, access controls and retention period.

Boundary: A successful HTTP response is not a quality verdict. Avoid putting raw prompts, secrets or personal data in public issues, workflow logs or artifacts.

PART 10 LLMOps is a versioned feedback loop

LLMOps joins development, evaluation, deployment and ongoing observation for systems that depend on language models. The reproducible unit is bigger than an application commit: a prompt, model or provider version, retrieval configuration, evaluator and data can all change the result.

The GitHub perspective

Use pull requests to review changes to prompts, application code, test cases and operational configuration together. Actions can run the team's tests and evaluation harness; protected environments can add deployment controls where available. Your selected model service and telemetry platform provide the runtime and production signals. GitHub Models is retired, so it is not that model service.

For each release, record the commit, prompt version, evaluation version and retrieval index or data version. Record the actual served model identifier when the provider supplies it; a model alias alone may not identify an immutable version. Do not promise exact replay when provider behavior or external data can change.

A four-week starting plan

  1. Week 1: Name an owner, user journey, risk boundaries and baseline signals. Inventory prompt, model and data dependencies.
  2. Week 2: Create synthetic regression cases and an independent holdout; agree quality and safety criteria with a reviewer.
  3. Week 3: Run the evaluation in a trusted delivery path, protect the release decision and record version identifiers.
  4. Week 4: Review sampled outcomes, latency and usage after release. Revert or pause on an agreed condition, and turn reviewed failures into new cases.

Boundary: Store secrets in an approved secret manager or CI secret facility, never in source, prompts, examples or logs. Review data access, retention and model-provider terms before using real records.
